## 内部設計書の形式

1行目は `# {{name}}`。見出しは次の 10 個を、この順に書く：`## 役割`、`## 公開インターフェース`、`## データ構造`、`## 処理の流れ`、`## 状態`、`## 依存関係`、`## エラー処理`、`## 並行性とタイミング`、`## 設定値と定数`、`## 外部とのやり取り`。下に `###` の見出しを足してよい。

## 機能の要求の形式

1行目は `# 3.1 機能（{{name}}）`、見出しは `## 機能の要求` である。要求は `- {{fr_prefix}}001: <文>` の形で、1行に1つ書く。番号は 001 から順に、重ねずに付ける。ID はバッククォートで囲まない。要求が1つもないときは、決まった1文だけを書く。要求の文は、1つの内容だけを、対象の名前と、条件か結果を入れて、確かめられる形で書く。

## 不明点の形式

1行に1つ、`- <文>` で書く。1つもないときは `- なし` の1行を書く。不明点を書く前に、解析メモ、照合の記録、ソースコードで答えを探す。見つからないものだけを書く。

## 書き方

- 日本語で書く。1行に1つの事実を書き、箇条書きと表を使う。
- 読み取れる内容がない節には、次の1文だけを書く：{{none_sentence}}
- ソースコードの名前と数値は、ソースコードの表記のまま、省略せずにバッククォートで囲む。名前の一部（接頭辞）を指すときは、接頭辞と `*` で書く。バッククォートは、ソースコードの名前と数値にだけ使う。
  - 例（作った名前）：`valve_open` は、`VLV_OK` を返す。`VALVE_*` の定数は、弁の番号を表す。
- 見出しと、表の見出しの行のバッククォートには、ソースコードにある名前だけを入れる。
- 条件付きコンパイルの中の内容は、条件の名前を書いて述べる（例：`USE_DRAIN` が定義されているとき、`valve_drain` を呼ぶ）。
- コメントと実装が合わないときは、実装の内容を書く。
- ソースコードと既存の設計書が食い違う内容は、ソースコードの内容を書く。
- 照合の記録の「一致した図」は、内容に合う見出しの下に、書き換えずに書く。
- 図は Mermaid で書く。1行目は `stateDiagram-v2`、`sequenceDiagram`、`flowchart TD`、`flowchart LR` のどれかにする。ラベルの中に `"` と `;` を書かない。`flowchart` の ID は英数字にし、箱と矢印のラベルは全部を二重引用符で囲む（`a["開く"] -->|"失敗"| b`）。`end` を ID にしない。`stateDiagram-v2` の日本語の名前は `state "閉じた状態" as s1` で付ける。`sequenceDiagram` の参加者は `participant c as 制御部` の形にする。
- 1ファイルは 1,000 行以下にする。リンクは書かない。

## 根拠の決まり

- ソースコードについての記述の根拠は、対象のソースファイルだけである。文書のファイル（md、txt、html など）は根拠にしない。
- 既存の設計書の内容の根拠は、渡した照合の記録だけである。

## してはいけないこと

- 設計書と機能の要求に、推測の言い回し（`と思われる`、`と考えられる`、`おそらく`、`かもしれない`、`はずである`、`と推測`）を書くこと。分からないことは、不明点に書く。
- 設計書と機能の要求に、根拠の場所（`ファイル名:行番号` の形、解析メモの根拠の場所、照合の記録の番号）を書くこと。
- `【既存設計書のみ】` の印と、`## 既存の設計書にだけ書かれている内容` の見出しを書くこと。スクリプトが入れる。
- 書く先のほかに、ファイルを書くこと。ソースコードを書き換えること。
