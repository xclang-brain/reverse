## 設計書の形式

- ひな形の1行目と見出しを、そのままの順に書く。下に見出しを足してよい。
- ひな形の決まった1文（{{none_sentence}}）は、その節に書く内容があるときだけ、内容に置き換える。読み取れる内容がない節には、決まった1文だけを残す。
- 要求の ID の接頭辞は {{id_prefix}} である。`なし` でないときは、要求を `- {{id_prefix}}001: <文>` の形で1行に1つ書く。番号は 001 から順に、重ねずに付ける。要求の文は、1つの内容だけを、対象の名前と、条件か結果を入れて、確かめられる形で書く。

## 不明点の形式

1行に1つ、`- <文>` で書く。1つもないときは `- なし` の1行を書く。不明点を書く前に、モジュールの設計書と照合の記録で答えを探し、ソースコードのフォルダの全体を Grep と Glob で探す。見つからないものだけを書く。

## 書き方

- 日本語で書く。1行に1つの事実を書き、箇条書きと表を使う。
- ソースコードの名前と数値は、ソースコードの表記のまま、省略せずにバッククォートで囲む。名前の一部（接頭辞）を指すときは、接頭辞と `*` で書く。バッククォートは、ソースコードの名前と数値にだけ使う。
  - 例（作った名前）：`valve_open` は、`VLV_OK` を返す。`VALVE_*` の定数は、弁の番号を表す。
- 見出しと、表の見出しの行のバッククォートには、ソースコードにある名前だけを入れる。
- モジュールは、モジュールの名前か、ファイルの名前（拡張子を付ける）で指す。要約の `pump/1` の形の名前は、分けたモジュールの部分の名前である。モジュールの名前は、後ろの `/1` を除いた `pump` である。`pump/1` はソースコードにない名前なので、検証担当が確かめられない。
  - 例（作った名前）：pump は、`valve.c` の `valve_open` を呼ぶ。
- 条件付きコンパイルの中の内容は、条件の名前を書いて述べる。
- コメントと実装が合わないときは、実装の内容を書く。ソースコードと既存の設計書が食い違う内容は、ソースコードの内容を書く。
- 図は Mermaid で書く。1行目は `stateDiagram-v2`、`sequenceDiagram`、`flowchart TD`、`flowchart LR` のどれかにする。`flowchart` の ID は英数字にし、箱と矢印のラベルは全部を二重引用符で囲む（`a["制御部"] -->|"呼ぶ"| b["弁"]`）。`stateDiagram-v2` の日本語の名前は `state "閉じた状態" as s1` で付ける。`sequenceDiagram` の参加者は `participant c as 制御部` の形にする。
- 1ファイルは 1,000 行以下にする。

## 根拠の決まり

- ソースコードについての記述の根拠は、対象のソースファイルだけである。
- 既存の設計書の内容の根拠は、渡した照合の記録だけである。

## してはいけないこと

- 設計書に、推測の言い回し（`と思われる`、`と考えられる`、`おそらく`、`かもしれない`、`はずである`、`と推測`）を書くこと。分からないことは、不明点に書く。
- 設計書に、根拠の場所（`ファイル名:行番号` の形、照合の記録の番号）を書くこと。
- `【既存設計書のみ】` の印と、`## 既存の設計書にだけ書かれている内容` の見出しを書くこと。スクリプトが入れる。
- 書く先が `書かない` のファイルを書くこと。
- 要求の ID を、バッククォートで囲むこと。
- Mermaid のラベルの中に `"` と `;` を書くこと。`sequenceDiagram` のメッセージに `#` を書くこと。
- `flowchart` の ID に、`end` を使うこと。
- リンクを書くこと。
- 文書のファイル（md、txt、html など）を根拠にすること。
- 書く先のほかに、ファイルを書くこと。モジュールの設計書とソースコードを書き換えること。
