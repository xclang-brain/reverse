# プラグインの設計

[要件と受入条件](requirements/specification.md) を実現するための設計。用語は、要件の文書の1章と同じである。禁止事項は、要件の文書の4章に書く。スクリプトの入出力、検査、値は、[スクリプトの仕様](script-spec.md) に書く。

## 1. 考え方

- **AI とスクリプトで分担する**：内容を読み取って書く仕事は、担当エージェントが行う。分け方、順番、検査、設計書の書き換え、一覧の作成は、スクリプトが行う。同じ入力から同じ手順になる。
- **1回に読む量を決める**：解析、変換、照合、検証の仕事には、量の上限を置く。執筆が読む照合の記録には上限がない（3.5）。大きなソースコードでも、この4つの担当が1回に読む量は変わらない。
- **書く担当と確かめる担当を分ける**：検証担当は、執筆担当が書いた全部の行に判定を付ける。スクリプトが、判定の根拠の場所を検査してから、設計書を直す。
- **状態はファイルに残す**：止まっても、同じコマンドで続きから進む。統括は、`next` の結果だけを見れば続けられる。
- **コマンドを動かすのは統括だけにする**：担当エージェントは、ファイルを読んで、ファイルに書く。`init` と `next` は、30 秒以内に返す（SR-80）。
- **根拠の場所は作業フォルダに残す**：解析メモ、照合の記録、判定の記録に、場所を書く。

## 2. フォルダの構成

```
.claude-plugin/marketplace.json      マーケットプレイスのマニフェスト（両方のツールで共通。plugin/ を指す）
plugin/                              配布するプラグイン（名前は reverse）
├── plugin.json                      GitHub Copilot CLI が読むマニフェスト
├── .claude-plugin/plugin.json       Claude Code が読むマニフェスト
├── com.github.copilot/agents/       担当エージェントの定義（5つ。両方のツールで共通）
├── hooks/                           担当エージェントの書き込みを出力先の中に限るフック（Claude Code。hooks.json と guard.py）
├── skills/make-design-docs/
│   ├── SKILL.md                     統括の手順
│   ├── scripts/revdoc.py            スクリプトの入口（バージョンの確認と、本体の読み込み）
│   ├── scripts/revdoclib/           スクリプトの本体
│   └── templates/                   指示のひな形（job-*.md）、設計書のひな形（docs/）
└── README.md
tests/                               自動テスト（A）と読み込みのテスト（B）
evals/                               評価（C）の道具：材料の取得、実行、採点、正解のファイル
docs/                                要求、要件、設計
.github/workflows/                   Windows と Linux で A を動かす（D）
```

- 担当エージェントの定義は1か所に置く。Claude Code のマニフェストの `agents` に、ファイルのパスを1つずつ書く。
- `.gitattributes` に `* text=auto eol=lf` を置く。

## 3. 処理の流れ

### 3.1 統括とスクリプト

統括の手順（SKILL.md）は、「`init` を呼ぶ。その後は、結果の `do` のとおりにする」である。

1. 統括が `init` を呼ぶ。`init` は、計画を作り、最初の `next` のコマンドを `do` に書いて返す。
2. 統括が `next` を呼ぶ。`next` は、前に渡した仕事の出来を検査し、次の仕事を最大4件返す。スクリプトだけで済む段階は、`next` の中で進む。
3. 統括が、仕事ごとに担当エージェントを、1つの返事の中でまとめて呼ぶ。伝えるのは、「指示のファイル（絶対パス）を読んで従う」の1文である。
4. 全部の結果が返ったら、統括が `next` をもう一度呼ぶ。`state` が done になるまで、2 〜 4 を繰り返す。
5. 統括が `serve` を呼び、結果の `do` のとおりに、利用者に日本語で伝える。

- `do` は、スクリプトが毎回書く英語の決まった文である。次に呼ぶコマンドの全文と、「担当エージェントの結果がすべて返ってから、次の `next` を呼ぶ」を含む。コンパクションで SKILL.md が統括のコンテキストから消えても、続けられる。
- `jobs` の `file` は、出力先からの相対パスで、ASCII の名前である。統括は、出力先の絶対パスとつないで、担当エージェントに渡す。
- 担当エージェントの最後の返事は、done の1語である。合否は、出力のファイルの検査で決める。
- SKILL.md には、「コマンドが終わるまで待つ。同じコマンドを重ねて動かさない」と書く。
- `<python>` のどのコマンドも見つからないときは、統括は、Python 3.9 以上が要ることを利用者に伝えて止まる。
- SKILL.md には、担当エージェントの呼び方の表を1つ置く。ツールごとの名前を書くのは、この表だけにする。

| ツール | 呼ぶツール | 担当の名前 | 結果を待つ指定 |
| --- | --- | --- | --- |
| Claude Code | Agent | `subagent_type` | `run_in_background: false` |
| GitHub Copilot CLI | task | `agent_type` | `mode: "sync"` |

- SKILL.md のフロントマターに `allowed-tools: Bash(python3:*) Bash(py:*) Bash(python:*) Write Edit Read Grep Glob` を書く。

### 3.2 段階

| 段階 | 行うもの | 単位 | 入力 | 出力 |
| --- | --- | --- | --- | --- |
| 準備 | スクリプト（`init`） | 全体 | ソースコード、PDF | 計画（ユニット、モジュール、仕事、PDF のページ数、ヘッダーとフッターの文字列）、UTF-8 のコピー、名前の集まり |
| 解析 | 解析担当 | ユニット | ソースファイルの行の範囲 | 解析メモ |
| 変換 | 変換担当 | PDF の 10 ページ | ページの画像、埋め込みテキスト、前後1ページの画像 | ページごとの Markdown |
| 組み立て | スクリプト | PDF | ページごとの Markdown | `docs/legacy/<PDF>/` |
| 照合 | 照合担当 | `docs/legacy/` の本文の 50 行まで | 番号を振った行、解析メモ、ソースコード | 照合の記録 |
| 振り分け | スクリプト | 全体 | 照合の記録 | モジュールごとの照合の記録 |
| 執筆（モジュール） | 執筆担当 | モジュール（ユニット5個まで） | 解析メモ、モジュールの照合の記録 | 内部設計書、機能の要求、不明点 |
| 検証 | 検証担当 | 設計書の本文の 50 行まで | 番号を振った行、ソースコード | 判定の記録 |
| 執筆（全体） | 執筆担当 | 1ファイル | 要約、モジュールの設計書、「全体」の照合の記録、ひな形 | 全体の内部設計書、要求仕様書の 3.1 以外の各章 |
| 検証（全体） | 検証担当 | 設計書の本文の 50 行まで | 検証と同じ | 判定の記録 |
| 仕上げ | スクリプト | 全体 | すべての出力 | 食い違いの一覧、不明点の一覧、入口のページ、`mkdocs.yml` |
| 表示 | スクリプト（`serve`） | 全体 | `docs/` | `site/`、表示用のサーバー、URL |

- ソースコードだけのときは、変換、組み立て、照合、振り分けを飛ばす。PDF だけのときは、準備、変換、組み立て、仕上げ、表示を行う。
- 指示のファイルには、読ませるソースファイルごとに「パス、開始行、終了行」を書く。初めの方に、「終わりの行まで読む。途中で切れたら、続きの行から読む」と1回書く。読ませるファイルの一覧が長いときは、一覧を別のファイルに出す。
- ユニットが5個を超えるモジュールは、ファイル名の順に5個ずつに分けて書く。照合の記録は、ソースファイル名で分けたファイルに割り当てる。ソースファイル名のない記録は、最初のファイルに入れる。
- 要約は、スクリプトがモジュールの設計書から作る（名前、行数、「役割」の最初の行、「依存関係」の先頭の 10 行まで。合計 2,000 行以下）。執筆担当は、要約で当たりを付け、必要なモジュールの設計書を開く。

### 3.3 不合格、失敗、再開

- スクリプトは、仕事ごとに、状態（まだ、渡した、済み、失敗）と回数を、状態のファイルに持つ。書くときは、一時ファイルに書いてから置き換える。設計書を書き換えるときも、同じにする。
- 不合格の仕事は、前の出力を `.work/rejected/` に移し、理由（行と直し方）を指示のファイルに書き足して渡し直す。出力のファイルがないことも、不合格に数える。
- 3回目も不合格の仕事は、失敗にする。3回目に書かれたファイルは残す。書かれなかったファイルには、スクリプトが代わりのファイルを置く（中身は、スクリプトの仕様の 4.5）。後の段階は、そのファイルを普通の出力として読む。行数だけが上限を超えた解析メモは、3回目にそのまま使う。
- 失敗の対象は、不明点の一覧の「処理の失敗」に載せる。入口のページには、段階ごとの失敗の数と、一覧へのリンクを載せる。
- その回の全部の仕事に出力がないときは、中断とみなし、回数を変えずに、同じ仕事を渡し直す。2回続いたら、`no_output` で止まり、その回の仕事の回数を1増やす。同じ仕事で止まり続けないためである。一部の仕事だけ出力がないときは、その仕事の回数を1増やす（検証の仕事を除く。検証は 3.6 のとおり）。
- 既知の制限：仕事が1件だけの回で、その仕事が毎回書けないときは、失敗になるまでに3回止まる。
- 再開の入口は、同じコマンドの1つである。`init` は、状態のファイルがあれば、計画を作り直して、保存した計画と比べる。比べるのは、対象のソースファイルと PDF の一覧とハッシュである。入力の場所か、ソースコードと PDF の組み合わせが変わったときも、違いに数える。外したファイルの増減は、違いに数えない。ビルドの出力やログが増えただけで、作業をやり直さずに済む。
- 同じなら、渡したままの仕事を「まだ」に戻して続ける。違えば、`input_changed` で止まり、違うファイルを伝える。
- 仕上げでも、同じ比べ方で入力を確かめ、違うファイルを不明点の一覧に載せる。担当エージェントが入力を書き換えたときに、利用者が気づけるようにするためである。
- 失敗した照合の仕事の記録は、形式に合う記録を使う。残りの行は、「照合していない」として扱う。

### 3.4 変換と組み立て

- 変換担当は、ページの画像を1ページ読むたびに、そのページのファイルを書く。書くページの画像を、会話のいちばん新しい画像にしておくためである。読んだ画像は会話に残り、後のリクエストにも入る。Copilot CLI は、モデルごとの上限を超えた画像をリクエストから外す。新しい画像を残す見込みである（実行ファイルの文で読んだ。動かしては確かめていない）。
- 書く内容がないページにも、空のファイルを書く。
- 指示のひな形に、表と記号の書き方の例を1行置く。図については、「書いた Mermaid を画像と見比べる」「図の範囲は、迷うときは広く書く」と書く。
- 前のページから続く表については、「前のページの表と同じ、表の1行目（列の名前の行）と区切りの行から書き始める。`#` の見出しは、そのページにあるものだけを書く。列の名前の行がない表は、1行目のセルを空にする」と書く。「同じ見出しの行を付ける」と書いていたときに、変換担当が、節の見出しを書き足したためである。
- 画像にした図の説明文には、図が何を表すかと、主な要素の名前を書く。線の通り道と本数を書くことは、指示の「してはいけないこと」に入れる（P-15）。細かく書いた説明文に、誤りが出たためである。
- 線が 30 本を超える図は、画像にする。線が約 45 本ある図を Mermaid に写すと、12 回のうち 7 回で、線のつなぎ先を誤ったためである（8章）。
- Mermaid の決まりに、「列に分かれた図は、列ごとに `subgraph` にする」「複数の列にまたがる横線は、1本を1つの箱にする」「複数の状態から出て合わさる線は、状態ごとの遷移に分ける」と書く。この形の図で、枠、横線、列の見出しの抜けが出たためである。
- 指示に、「図の題は、ページにあるとおりに、図の後ろに書く」と書く。文字化けのページは文字列の検査がなく、図の題の書き落としを、スクリプトが見つけられないためである。
- Unicode に対応づけられない文字が 5% を超えるページは、埋め込みテキストを使わない（SR-37）。変換担当は、画像だけから書く。PDF の全体では 5% 以下でも、図のページだけが文字化けしている PDF があるためである（8章）。
- 図は、種類で書き方を決める。表にない種類の図は、箱と線で表せるなら `flowchart`、表せないなら画像にする。図の中の文字が読めない図も、画像にし、説明文に `【判読できない】` を書く。

| 図の種類 | 書き方 |
| --- | --- |
| 状態遷移図 | `stateDiagram-v2` |
| シーケンス図 | `sequenceDiagram` |
| ブロック図、構成図、フローチャート | `flowchart`（入れ子は `subgraph`） |
| タイミングチャート、波形、グラフ、写真、画面の絵、位置や並びに意味がある図、線が 30 本を超える図 | 画像（`figure:` の行と説明文） |

- Mermaid は、検査（スクリプトの仕様の 5.4）に合格する書き方を、変換と執筆の指示に書く。
- ヘッダー、フッター、ページ番号、行番号は、`init` が PDF ごとに決める（スクリプトの仕様の 2.6）。指示のファイルには、「書かなくてよい文字列」として、位置と一緒に載せる。「表や本文の一部として見えるときは書く」と添える。
- 文字列の検査（SR-33）は、前後1ページを含めて比べる。段落が仕事の境目のページをまたぐときに、前の仕事の出力を見るためである。
- 組み立てでは、スクリプトが、ページの目印を入れ、見出しのレベルをそろえ、図を切り出す（スクリプトの仕様の 8.1）。レベルをそろえるのは、`2.5.9` の形の番号で始まる見出しである。ほかの見出しは、変換担当が書いたレベルのままにする。
- 図は、`figure:` の範囲に余白を足して切り出す。変換担当が書く範囲が、図より少し狭いことがあるためである。

### 3.5 照合と、既存の設計書にしかない内容

- 照合担当は、解析メモを Grep で探して場所の見当を付け、その場所のソースコードを読んでから分類する。行が述べている値、条件、順序、状態、エラーコードを、ソースコードの式と1つずつ比べる。指示のひな形に、この進め方を番号の順に書く。
- 指示のひな形に、食い違いの決まりと例を書く（設計書は 30 秒、コードは 60 秒）。ソースコードにだけ細かい内容があるときは、「一致」にする。既存の設計書の別の場所を見ないと決められないときは、「既存設計書のみ」にする。「既存設計書のみ」の記録の文は、それだけで意味が通るように、対象の名前を補って書く。
- 照合は、文ごとに行う。1つの段落に、ソースコードと一致する文、食い違う文、既存の設計書にしかない文が混ざるためである（小さい材料で、既存の設計書にしかない記述 10 件のうち2件が、ほかの文と同じ段落にあって、新しい設計書に入らなかった）。
- 「既存設計書のみ」にする前に、文の語で、解析メモの全部を探し直す。設定やテンプレートのファイルにだけ書かれた内容の見落としが多かったためである。「既存設計書のみ」の記録は、文ごとに分ける。2回目の「一致」で、文ごとに外せるようにするためである。この2つを、照合の指示のひな形に書く。
- 照合は、同じ文を2回、別々の照合担当が行う（SR-83）。2回目の記録からは、食い違いを足す。1回目の「既存設計書のみ」の記録は、2回目が全部を「一致」としたときに外す。ほかの分類と内容は、1回目の記録で決める。
- 画像で載せた図は、食い違いでなければ「既存設計書のみ」にする。画像は、ソースコードと1つずつ照らせないためである。
- PDF の名前とページは、スクリプトが、行の番号とページの目印から求める。範囲がページをまたぐときは、始まりのページを載せる。食い違いのモジュールは、ソースコードの場所から求める。
- 「一致」の範囲にある Mermaid の図は、スクリプトが、場所のモジュールの照合の記録に載せる（SR-81）。執筆の指示のひな形に、「『一致した図』は、内容に合う見出しの下に、書き換えずに書く」と書く。
- 「既存設計書のみ」の記録は、スクリプトが、内部設計書の見出し「既存の設計書にだけ書かれている内容」の下に入れる（SR-54）。スクリプトが入れるので、全部の記録が印つきで入る。1,000 行を超えるときは、続きのファイル（`<拡張子を除いたファイル名>~p2.md`）に分ける。
- 「既存設計書のみ」の記録のコードスパンには、照合の記録の検査で、名前の検査（SR-65）を当てる。この見出しから後ろの行は、行の検査（SR-58）の対象から外す。既存の設計書の内容で、`check` が不合格になるのを防ぐためである。
- 執筆担当は、設計書の本文に、ソースコードで確かめられる内容だけを書く。「既存設計書のみ」の記録の内容は、本文に書かない（スクリプトが、印を付けて入れる）。本文に書くと、検証で消えて、不明点の一覧に載る（小さい材料の1回で、抜き取った不明点 10 件のうち4件が、これだった）。執筆の指示のひな形の「してはいけないこと」に書く。
- 全体の文書では、モジュールを、モジュールの名前かファイルの名前で指す。分けたモジュールの部分の名前（`kernel/1` の形）は、ソースコードにない名前で、検証担当が確かめられないためである。
- 要求仕様書のひな形の決まった1文は、使った入力に合わせる。ソースコードだけのときは、ソースコードだけを挙げる文にする。
- 執筆担当が、既存の設計書の内容として読むのは、モジュールの照合の記録だけである。食い違いと一致した図の記録は、全部読む。「既存設計書のみ」の記録は、不明点の答えを探すためだけに使う（SR-55）。量に上限がないので、語で探して、当たった記録（`### E…` から次の `### ` の前まで）だけを読む。指示のひな形にも、同じ文を書く。
- 印のない本文は、ソースコードから書いた内容と、ソースコードと一致した既存の設計書の図になる。一致した図は、照合担当が確かめているので、検証の対象から外す。

### 3.6 検証

- 状態の決まりは1つである。スクリプトは、ファイルごとに、確かめた行（節の見出しの並びと、行の文）を記録する。対象の行は、OK または対象外の判定が検査（SR-61）に合格するまで、検証の仕事にする。
- この決まりで、次のことを行う：最初の検証、不合格の番号だけの渡し直し、置き換えた文の再検証、再開、検証担当が設計書を直接書き換えたときの検出。
- バッククォートの名前を含む行の判定は、OK、NG、不明のどれかにする。Mermaid のブロックの NG は、不明と同じに扱う。
- 名前の検査（SR-65）は、執筆の出力では、見出しと、表の見出しの行に当てる。この2つは、検証で書き換わらないためである。本文の行の名前は、検証の判定の検査（SR-61）と `check` で見る。執筆の渡し直しを増やさないためである。
- 不明の判定は、1回では行を消さない。次の回に、別の検証担当がもう一度確かめ、2回続けて不明のときに消す。1回の不明で消すと、消した行のうち、ソースコードで確かめられるものが残った（小さい材料の1回で、不明点の一覧の「検証で確かめられなかった行」5件のうち3件）。
- 検証の仕事は、不合格の判定があっても済みにする。判定が付かなかった行を、次の回の新しい仕事にする。3回目の後に残った行は、設計書から消して、不明点の一覧に載せる。`check` に合格する設計書が残る。
- 判定の根拠の場所は、1行に3個まで書ける。ファイル名のように、ソースファイルのパスにある語は、根拠のファイルにあるものとして扱う。
- 検証担当の指示のひな形に、判定の例を置く。
  - 「3回までやり直す」は、コードで確かめられれば OK。「通信が不安定なため3回にしている」は、コメントにもコードにも書かれていなければ不明。
  - `#if` の中の処理を条件なしで述べた行は NG にし、条件を書いた文に直す。
  - 行の一部だけを確かめられたときは NG にし、確かめられた部分だけの文に直す。
  - 図や表を案内するだけの行（「次の図に示す」）は、事実を述べていないので、対象外にする。
- 根拠の場所が条件付きコンパイルの中にある行には、スクリプトが、条件の注を足す（SR-84）。条件の名前を書くことを、担当エージェントの指示だけに任せると、抜けが残った（小さい材料で、抜き取った 30 行のうち4行）。
- 決まった1文は、検証の対象から外す。
- 「既存設計書のみ」の印の付いた文と、執筆担当が書いた不明点も、検証担当が確かめる（SR-85）。ソースコードで確かめられた「既存設計書のみ」の文と、答えが見つかった不明点を外す。照合担当と執筆担当だけに任せると、ソースコードで分かる内容が、2〜3割残った（小さい材料で、抜き取った 10 件のうち、多い回で3件）。検証の指示のひな形に、この2種類の行の判定のしかたを書く。

## 4. 出力先の構成

```
<出力先>/
├── mkdocs.yml
├── docs/
│   ├── index.md                     入口のページ
│   ├── requirements/                要求仕様書（ISO/IEC/IEEE 29148:2018 の SRS の構成）
│   │   ├── 1-introduction.md 〜 5-appendices.md   章と節ごとのファイル
│   │   └── 3-1-functions/<モジュールの名前>.md    機能の要求（モジュールごと）
│   ├── design/
│   │   ├── architecture.md          全体の内部設計書
│   │   └── modules/<モジュールの名前>.md          モジュールの内部設計書
│   ├── legacy/<PDF>/                既存の設計書を Markdown にしたもの。fig/ に切り出した画像
│   └── review/
│       ├── discrepancies.md         食い違いの一覧（続きは discrepancies~p2.md）
│       └── unknowns.md              不明点の一覧（続きは unknowns~p2.md）
├── site/                            HTML
└── .work/                           作業フォルダ
```

- モジュールのページは、ソースコードのフォルダと同じ階層に置く。モジュールの名前は、フォルダのパスからスクリプトが決める（直下は `_root`。決まりは、スクリプトの仕様の 2.4）。分けたモジュールは `<モジュールの名前>/<番号>.md` に書き、そのモジュールの入口のページ（分けたファイルと、扱うソースファイル名の一覧）を、仕上げで作る。
- 内部設計書の見出しは、IEEE 1016（ソフトウェア設計記述）の観点をもとにする。
- 要求の ID の接頭辞は、スクリプトが決めて、指示のファイルで渡す（機能は `FR-<モジュール>-001`、性能は `PR-001` など）。
- `mkdocs.yml` は、SR-68 を満たす設定にする（スクリプトの仕様の 10章）。`privacy` プラグインが、ビルドのときに mermaid.min.js を unpkg.com から取得して、サイトに含める。取得できないときも、ビルドは成功し、HTML は unpkg.com を参照する（mkdocs-material 9.8.2 で確かめた）。検索の索引は、ビルドのたびに、フック（`.work/search_hook.py`）が直す。mkdocs-material の検索が、問い合わせの漢字の並びを、索引にある語で書き換えるためである（8章）。
- 入口のページのモジュールの一覧には、モジュールの名前とフォルダのパスを載せる。
- 2つの一覧の項目は、スクリプトの仕様の 8.7 に書く。一覧も、1ファイルを 1,000 行以下に分ける。

## 5. スクリプト

### 5.1 サブコマンド

| サブコマンド | 役割 |
| --- | --- |
| `init` | 入力と Python パッケージを確かめ、計画を作る。状態があれば再開する。 |
| `next` | 前に渡した仕事を検査し、スクリプトだけで済む段階を進め、次の仕事を返す。変換の仕事を渡す直前に、そのページの画像と埋め込みテキストを作る。 |
| `check` | 全部のファイルに検査の決まりを当て直し、不合格の項目と、失敗した仕事の数を返す。`next` と同じ検査の関数を使う。 |
| `serve` | 切り離したプロセスを1つ始める。そのプロセスが、`mkdocs build`、続けて `mkdocs serve` を動かす。最長 20 秒待って、状態を返す。もう一度呼ばれたときは、動いているプロセスの状態を返す。 |
| `stop` | サーバーを止める。 |

入口のファイル、エラー、名前の集まり、サーバーの決まりは、スクリプトの仕様の 1.1、1.3、2.9、11章に書く。

### 5.2 値

値（行数、回数、割合）は、要件の文書とスクリプトの仕様に書く。スクリプトでは、1か所に定数で置く。利用者が変える設定にはしない。

評価（C）で、不合格の原因が値にあると分かったときは、要件の文書、スクリプトの仕様、テスト、定数の順に直し、C をやり直す（要件の文書の6章）。次の値は、変えるときの向きを決めておく。

| 値 | 値のある所 | 変えるときの向き |
| --- | --- | --- |
| 変換の仕事のページの数 | SR-25 | Copilot CLI で、画像の数の上限のためにページを読めないときは、減らす。 |
| 検証の仕事の行数 | SR-59 | 検証する範囲を減らさずに、行数を増やす。行数を増やしても、2回目と3回目の仕事の数は、行が残ったファイルの数より減らない。 |

## 6. 担当エージェント

| 担当 | 名前 | 使えるツール | 仕事 |
| --- | --- | --- | --- |
| 解析 | `reverse:code-analyst` | Read、Grep、Glob、Write | ユニットのソースコードを読み、根拠の場所つきの解析メモを書く。 |
| 変換 | `reverse:pdf-converter` | Read、Write | ページの画像を読み、1ページずつ Markdown に書く。 |
| 照合 | `reverse:doc-matcher` | Read、Grep、Glob、Write | 既存の設計書の全部の行を、ソースコードと照らして分類する。 |
| 執筆 | `reverse:doc-writer` | Read、Grep、Glob、Write | 内部設計書と要求仕様書を書く。 |
| 検証 | `reverse:doc-verifier` | Read、Grep、Glob、Write | 執筆担当が書いた全部の行に、判定を付ける。 |

- どの担当も、指示のファイルを読んで仕事をする。定義と指示のひな形には、「ファイルを読む」「ファイルに書く」と書く。
- どの指示にも、「書くファイルは、指示のファイルの『書く先』だけである」と書く。書いたファイルを直すときは、同じファイルの全体を書き直す、とも書く。
- Claude Code では、フックで、担当エージェントの書き込みを出力先の中に限る（SR-86）。指示だけでは、約 700 回に1回、担当エージェントが作業フォルダに関係のないファイルを作った。大きい材料では、担当エージェントを 3,000 回以上呼ぶ。
  - `hooks/hooks.json` に、Write と Edit の前に動くフック（PreToolUse）を1つ書く。コマンドは `python3 "${CLAUDE_PLUGIN_ROOT}/hooks/guard.py" || py -3 "…" || python "…" || exit 0` とする。Python が見つからないときと、スクリプトが失敗したときは、書き込みを通す。
  - `guard.py` は、標準入力の JSON を読む。`agent_type` が `reverse:` で始まらないときは、何も出さずに終わる（ほかの作業の書き込みに触らない）。
  - 書く先（`tool_input.file_path`。相対パスは `cwd` から）の親のフォルダを上へたどり、`.work/state.json` があるフォルダを、出力先とする。書く先は、シンボリックリンクを解いたパスで比べる（リンクを通して、出力先の外に書かせない）。書く先が、出力先の `.work/` か `docs/` の下にあり、`.work/state.json` と `.work/plan.json` でないときだけ、通す。
  - 止めるときは、終了コード 0 で、`{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "<理由>"}}` を標準出力に書く。理由は、英語の1文で、指示のファイルの「書く先」だけに書くように伝える。
  - `guard.py` は、標準ライブラリだけを使い、古い Python でも動く書き方にする（`revdoc.py` と同じ）。
- 解析、照合、執筆、検証の指示には、「ソースコードについての記述の根拠は、対象のソースファイルだけ」と書く。照合の指示には「既存の設計書の内容の根拠は、番号を振った行だけ」、執筆の指示には「既存の設計書の内容の根拠は、渡した照合の記録だけ」と続けて書く。
- 照合と検証の指示には、「記録の内容と直した文のうち、日本語でない文は、日本語に直して書く。名前と数値は、元の表記のまま書く」と書く。スクリプトが、その文をそのまま設計書と一覧に入れるためである。
- 解析メモの項目は、設計書に載せる内容を、関数、型、定数の集まりなどの単位で書く。
- 執筆の指示には、「1行に1つの事実を書き、箇条書きと表を使う」と書く。
- 執筆と検証の指示には、名前の書き方の例を書く。名前は全体を書く。名前の一部（接頭辞）を指すときは、`VALVE_*` の形で書く。
- 指示のひな形の例の名前は、作った名前にする（P-13）。スクリプトの仕様の6章の例の名前は、ひな形に写さない。
- 検証担当が書くのは、判定の記録だけである。Copilot CLI では、Write の指定で edit も渡るので、設計書の直接の書き換えは、3.6 の状態の決まりで見つける。

- Claude Code では、プラグインのフックが、担当エージェントの書き込みを出力先の中に限ること。Python のコマンドが見つからないときは、働かないこと。

- `'` を含むパスは使えないこと。Windows では、出力先を短いパスにすること。
- サーバーの注意：サンドボックスを有効にした Linux の Copilot CLI では、ブラウザーからつながらない見込みである。Windows では、ツールを終えるとサーバーも止まることがある。
- Copilot CLI、Windows、29148 の構成については、確かめた範囲を書く。「準拠」と書かずに、「29148:2018 の SRS の構成で書く」と書く。

| 入れないもの | 足す条件 |
| --- | --- |
