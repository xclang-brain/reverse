# プラグインの設計

[要件と受入条件](requirements/specification.md) を実現するための設計。

## 1. 考え方

- **AI とスクリプトの分担**：内容を読み取って書く仕事は、担当エージェントが行う。分け方、順番、形式の検査、まとめは、スクリプトが行う。同じ入力から同じ手順になるようにするためである。
- **担当を分ける**：担当エージェントごとに、読む範囲を小さくする。大きなソースコードでも、1回に読む量は一定になる。
- **書く担当と確かめる担当を分ける**：検証担当は、執筆担当の作業の経緯を知らない状態で、ソースコードと照らし合わせる。
- **状態はファイルに残す**：途中で止まっても、続きから再開できる。

## 2. フォルダの構成

```
plugin/                              配布するプラグイン
├── plugin.json                      GitHub Copilot CLI が読むマニフェスト（Agent Plugins の形式）
├── .claude-plugin/plugin.json       Claude Code が読むマニフェスト
├── com.github.copilot/agents/       担当エージェントの定義（両方のツールで共通）
│   ├── code-analyst.agent.md        解析担当
│   ├── pdf-converter.agent.md       変換担当
│   ├── doc-matcher.agent.md         照合担当
│   ├── doc-writer.agent.md          執筆担当
│   └── doc-verifier.agent.md        検証担当
├── skills/make-design-docs/
│   ├── SKILL.md                     スキルの手順
│   ├── scripts/revdoc.py            スクリプトの入口
│   ├── scripts/revdoc/              スクリプトの本体
│   └── templates/                   設計書のひな形
└── README.md
tests/                               スクリプトの自動テストと読み込みのテスト
evals/                               実際に動かす評価の道具
docs/                                要求、要件、設計
```

担当エージェントの定義は1か所に置く。Claude Code のマニフェストは、`agents` の項目でこのファイルを指す。

## 3. 処理の流れ

スキルは、スクリプトの `next` を繰り返し呼ぶ。`next` は、前に渡した仕事の出来を検査し、次の仕事を最大4件返す。スキルは、仕事ごとに担当エージェントを並列で呼ぶ。段階の順番と、スクリプトだけで済む処理は、`next` の中で進む。

| 段階 | 行うもの | 単位 | 入力 | 出力（`.work/` は作業フォルダ） |
| --- | --- | --- | --- | --- |
| 準備 | スクリプト（`init`） | 全体 | ソースコード、PDF | `.work/state.json`、`.work/inventory.json`、`.work/pages/` |
| 解析 | 解析担当 | ユニット | ソースコード | `.work/notes/<ユニット>.md` |
| 変換 | 変換担当 | PDF の10ページ | ページの画像とテキスト | `.work/converted/<PDF>/<番号>.md` |
| 組み立て | スクリプト | PDF | 変換した Markdown | `docs/legacy/<PDF>/` |
| 照合 | 照合担当 | 既存の設計書の1ファイル | 既存の設計書、解析メモ、ソースコード | `.work/match/<番号>.md` |
| 振り分け | スクリプト | 全体 | 照合の記録 | `.work/match-by-module/<モジュール>.md` |
| 執筆（モジュール） | 執筆担当 | モジュール | 解析メモ、振り分けた照合の記録 | `docs/design/modules/<モジュール>.md`、`docs/requirements/3-1-functions/<モジュール>.md`、`.work/unknowns/<モジュール>.md` |
| 検証 | 検証担当 | モジュール | 上の2つの設計書、ソースコード | 設計書の修正、`.work/verify/<モジュール>.md` |
| 要約 | スクリプト | 全体 | モジュールの設計書 | `.work/digest.md` |
| 執筆（全体） | 執筆担当 | 全体の内部設計書、要求仕様書の残りの章 | 要約、モジュールの設計書、照合の記録 | `docs/design/architecture.md`、`docs/requirements/` の各章 |
| 仕上げ | スクリプト | 全体 | すべての出力 | `docs/review/`、`docs/index.md`、`mkdocs.yml`、検査の結果 |
| 修正 | 執筆担当 | 検査で不合格の項目 | 検査の結果 | 設計書の修正 |
| 表示 | スクリプト（`serve`） | 全体 | `docs/` | `site/`、表示用のサーバー |

- 解析と変換は、互いに依存しないので、同じ回にまとめて渡す。
- ソースコードだけのときは、変換、組み立て、照合、振り分けを飛ばす。
- PDF だけのときは、変換、組み立て、仕上げ、表示だけを行う。

## 4. 出力先の構成

```
<出力先>/
├── mkdocs.yml
├── docs/
│   ├── index.md                     入口のページ
│   ├── requirements/                要求仕様書（ISO/IEC/IEEE 29148:2018 の SRS の構成）
│   │   ├── index.md
│   │   ├── 1-introduction.md        1 はじめに
│   │   ├── 2-references.md          2 参考文献
│   │   ├── 3-1-functions/           3.1 機能（モジュールごとに1ファイル）
│   │   ├── 3-2-performance.md       3.2 性能
│   │   ├── 3-3-usability.md         3.3 ユーザビリティ
│   │   ├── 3-4-interfaces.md        3.4 インターフェース
│   │   ├── 3-5-database.md          3.5 論理データベース
│   │   ├── 3-6-design-constraints.md 3.6 設計制約
│   │   ├── 3-7-attributes.md        3.7 ソフトウェアシステム属性
│   │   ├── 3-8-supporting.md        3.8 補足情報
│   │   ├── 4-verification.md        4 検証
│   │   └── 5-appendices.md          5 付録
│   ├── design/                      内部設計書
│   │   ├── architecture.md          全体
│   │   └── modules/                 モジュールごとに1ファイル
│   ├── legacy/<PDF>/                既存の設計書を Markdown にしたもの
│   └── review/
│       ├── discrepancies.md         食い違いの一覧
│       └── unknowns.md              不明点の一覧
├── site/                            HTML の静的サイト
└── .work/                           作業フォルダ
```

- 内部設計書の見出しは、IEEE 1016（ソフトウェア設計記述）の観点をもとに決めた。
- モジュールのファイル名は、フォルダのパスの `/` を `-` に置き換えたものとする。ソースコードの直下のファイルは `root` とする。

## 5. スクリプト

入口は `scripts/revdoc.py` の1つで、次のサブコマンドを持つ。標準出力には、ASCII の JSON だけを書く。

| サブコマンド | 役割 |
| --- | --- |
| `init` | 入力と Python パッケージを確かめ、ユニットとモジュールに分け、PDF をページの画像にする。状態がすでにあれば、続きから始める。 |
| `next` | 前に渡した仕事の出来を検査し、次の仕事を返す。仕事の指示は `.work/tasks/<番号>.md` に書き、標準出力には番号、担当エージェントの名前、指示のファイルのパスを書く。 |
| `status` | 段階と件数を返す。 |
| `check` | 出来上がった設計書の構造を検査する。 |
| `serve` | 静的サイトを作り、表示用のサーバーを起動して URL を返す。 |
| `stop` | 表示用のサーバーを止める。 |

### 形式の検査（`next` の中）

| 仕事 | 合格の条件 |
| --- | --- |
| 解析 | 出力のファイルがあり、決まった見出しがそろっている。 |
| 変換 | 出力のファイルがあり、担当したすべてのページの目印（`<!-- page: N -->`）がある。PDF に埋め込まれたテキストがあるときは、その文字の8割以上が出力に含まれる。 |
| 照合 | 出力のファイルがあり、決まった見出しと項目の形式になっている。 |
| 執筆、検証 | 出力のファイルがあり、決まった見出しがそろっている。 |

不合格のときは、理由を指示のファイルに書き足して、同じ仕事を渡し直す。3回目も不合格なら、その仕事を失敗として不明点の一覧に載せ、先へ進む。

## 6. 担当エージェント

| 担当 | 名前 | 使えるツール | 仕事 |
| --- | --- | --- | --- |
| 解析 | `reverse:code-analyst` | 読む、探す、書く | ユニットのソースコードを読み、解析メモを書く。 |
| 変換 | `reverse:pdf-converter` | 読む、書く、コマンドの実行 | ページの画像を見て、Markdown に書き起こす。細かい文字は、スクリプトで拡大した画像を見る。 |
| 照合 | `reverse:doc-matcher` | 読む、探す、書く | 既存の設計書の記述をソースコードと照らし合わせる。 |
| 執筆 | `reverse:doc-writer` | 読む、探す、書く、直す | 内部設計書と要求仕様書を書く。 |
| 検証 | `reverse:doc-verifier` | 読む、探す、書く、直す | 執筆担当が書いた設計書を、ソースコードと照らして直す。 |

- どの担当にも、スキルを呼ぶツールと、ほかのエージェントを呼ぶツールを渡さない。担当エージェントがスキルの手順を自分で始めてしまうのを防ぐためである。
- 担当エージェントは、渡された指示のファイルを読んで仕事をし、最後に「完了」とだけ返す。

## 7. 開発で確かめた事実

| 確かめたこと | 結果 | 確かめた版 |
| --- | --- | --- |
| 1つのフォルダを両方のツールが読み込めるか | 読み込める。Copilot CLI は直下の `plugin.json` を、Claude Code は `.claude-plugin/plugin.json` を読む。 | Claude Code 2.1.330、Copilot CLI 1.0.114 |
| 担当エージェントの定義を1か所に置けるか | 置ける。Claude Code のマニフェストの `agents` に、`com.github.copilot/agents/` のファイルを1つずつ書く。フォルダの指定は受け付けない。 | 同上 |
| Copilot CLI が画像を読めるか | 読める。`view` ツールの説明に、画像を返すとある。 | Copilot CLI 1.0.114（モデルに届くツールの定義で確認） |
| Claude Code でプラグインのスキルを対話なしで呼べるか | 呼べる。`claude -p "/プラグイン:スキル" --plugin-dir フォルダ` で、スキルのフォルダの場所もモデルに届く。 | Claude Code 2.1.330 |
| PDF を画像にできるか | pypdfium2 で、A4 の1ページを 150 dpi（1241×1754 ピクセル）にできる。日本語の埋め込みテキストも取り出せる。 | pypdfium2 5.13.0 |
