# 要求一覧

このプラグインで実現したいことを、依頼者との対話から整理したもの。この一覧をもとに、要件と受入条件を決める。

- 「出どころ」の H1 〜 H7 は、[ヒアリングの記録](hearing-log.md) の見出しの番号である。
- 優先度は、現時点ではすべて必須とする。
- 版と変更履歴は Git で管理する。

## 1. 目的

- **課題**：既存製品の拡充開発を AI で進めたいが、既存の設計書は AI が読みやすい形になっておらず、内容がソースコードと合っていないことも多い。
- **目的**：ソースコードと既存の設計書から、AI が読める正しい設計書を作り、その設計書をもとに今後の開発を進められるようにする。
- **成功の状態**：どのような製品のソースコードや既存の設計書でも、同じ手順で新しい設計書を作れる。AI は Markdown で、人間は HTML で、その設計書を読める。

## 2. 関係者

| 関係者 | 関わり方 |
| --- | --- |
| 依頼者 | 要求を決め、承認する。 |
| 利用者（製品の開発者） | プラグインを動かし、完成した設計書と一覧を確認する。設計書を HTML で読む。 |
| 拡充開発を行う AI | 設計書を Markdown で読み、開発に使う。 |
| 開発者（AI） | このプラグインを作る。 |

## 3. 要求

状態はすべて「承認済み」である（2026-11-22、依頼者が承認。H6、H7）。

### 3.1 設計書を作る

| ID | 要求 | 出どころ |
| --- | --- | --- |
| R-01 | ソースコードを読み取り、リバースエンジニアリングで設計の内容を取り出す。 | H1 |
| R-02 | 既存の設計書（PDF）を画像認識で読み取り、Markdown に変換する。PDF に文字のデータが埋め込まれているときは、読み違いの確認に使う。 | H1、H7 |
| R-03 | R-01 と R-02 の結果を合わせて、新しい設計書を Markdown で作る。新しい設計書は、AI が読んで開発に使うことを主な目的とする。 | H1 |
| R-04 | ソースコードだけ、または PDF だけの製品でも使える。ソースコードだけのときはコードから新しい設計書を作り、PDF だけのときは PDF を Markdown に変換する。 | H5 |
| R-05 | どのようなソースコードや既存の設計書でも、同じ手順で設計書を作れる。最初の対象は、10万行から100万行の組み込み機器のソフトウェア（C、C++）とする。 | H1、H3、H5 |

### 3.2 新しい設計書の内容

| ID | 要求 | 出どころ |
| --- | --- | --- |
| R-06 | 要求仕様（何をするか）と内部設計（どう作られているか）の両方を書く。要求仕様は ISO/IEC/IEEE 29148 の構成に従い、内部設計は別の構成で書く。 | H1、H2 |
| R-07 | ソースコードと既存の設計書の内容が食い違うときは、ソースコードの内容を書き、食い違いを一覧に記録する。一覧の各項目には、既存の設計書での場所（PDF の名前とページ）と、ソースコードでの場所（ファイル名と関数名）を載せる。 | H2、H7 |
| R-08 | 既存の設計書にしか書かれていない内容は、新しい設計書に入れ、既存の設計書から取った内容でコードでは確かめていないことを示す。 | H2 |
| R-09 | ソースコードからも既存の設計書からも分からないことは、不明点の一覧に記録する。設計書には、読み取れた事実を書く。 | H4 |
| R-10 | 既存の設計書の中の図は、Mermaid 記法のテキストに書き直す。Mermaid で表せない図（タイミングチャート、波形、写真、画面の絵など）は、PDF から切り出した画像を載せ、短い説明文を付ける。 | H5、H7 |
| R-11 | 新しい設計書は、適切な単位でファイルを分ける。 | H1 |
| R-16 | 新しい設計書は、日本語で書く。ソースコードのコメントや既存の設計書が何語でも同じである。 | H6 |

### 3.3 人間が読むための静的サイト

| ID | 要求 | 出どころ |
| --- | --- | --- |
| R-12 | Markdown の設計書を MkDocs で HTML の静的サイトにし、その PC のブラウザーで見られる状態にする。 | H1、H5 |

### 3.4 進め方

| ID | 要求 | 出どころ |
| --- | --- | --- |
| R-13 | 利用者がソースコードと PDF の場所を指示したら、最後まで自動で進める。利用者は、完成した設計書、食い違いの一覧、不明点の一覧を確認する。 | H4 |

### 3.5 配布と動作環境

| ID | 要求 | 出どころ |
| --- | --- | --- |
| R-14 | エージェントプラグインの形式で配布し、GitHub Copilot CLI と Claude Code で動く。 | H1、H3 |
| R-15 | Windows と Linux で動く。 | H3 |

## 4. 今回の範囲に入れないもの

- Word や Excel などから PDF への変換（利用者が事前に行う）
- 設計書ができた後の更新（日々の開発の中で、コードを直す人や AI が設計書も直す）
- 静的サイトの公開（社内サーバーや GitHub Pages などへの配置）
- VS Code の GitHub Copilot と macOS での動作
- 新しい設計書の本文に、記述ごとの根拠の場所（ソースファイル名と関数名、PDF のページ番号）を示すこと（H6）

## 5. 開発の進め方

- 要求が決まった後は、開発者（AI）が自律的に開発する。（H1）
- テストには、公開されている組み込み向けの OSS を使う。OSS は開発者（AI）が選ぶ。（H4）
- 開発は、要件の作成から評価までを、途中で止まらずに最後まで進め、完成したら PR を作る。（H7）
- 評価に使う利用量に、上限は決めない。約1万行の小さい材料と、10万行以上の材料の両方で、合格するまで動かす。（H7）
