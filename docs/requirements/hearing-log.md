## 2026-11-22 最初の要望（原文）

> 今からこのプロジェクトで作る、ツールについて伝えます。 ただ、最初のコンスティチューションに書いてある通り、要求までは私と会話をしながら進めていきたいです。その後は AI、あなたに自律的に作っていただきたいです。このプロジェクトで、作るのは、ソースコードおよび既存の、設計書から、新しく AI が読める形の、設計書を作るということです。つまり、ソースコードからリバースエンジニアリングで、設計書を作るという点プラス、既存の設計書 PDF 形式の設計書を画像認識により、マークダウンに変換するというのを両方でやり、その上で、新しい設計書を作る、マークダウン形式の新しい形式、設計書を作ります。そしてこの、設計書はISO/IEC/IEEE 29148準拠 としたいです。その上で、このツールは、GitHub Copilot や Claude Code で使えるエージェントプラグイン形式で、配布したいです。そしてその上で、マークダウンは、AI が見るように作ります。つまり、リバースエンジニアリングで作成した設計書をもとに、今後の開発を進めたいということです。まあ、背景としては、今 AI を、活用した、開発が進んではいますが、新しく一から、製品を作ることは、少なくて、既存の製品の拡充開発がメインです。しかし既存の、製品の開発は、今まで人間がやってきたため、ドキュメントが AI ライクになっていないですし、なんだったらみんなドキュメントよりコードを正として、扱っており、ドキュメントがすべて正しいかもわからない状況です。結構間違ってることも多いです。 そのため既存の、ドキュメントを PDF 化し、それをマークダウン形式にするのと同時に、リバースエンジニアリングの観点でも、設計書を再度一から作りたいということです。そしてその設計書は、AI はマークダウンで取り扱いますが、人間は HTML 形式で見るようにしたいので、適切にファイル分割し、MKDocs で HTML の静的サイト化したいです。ここまでが今回作るツール、エージェントプラグインでやれるようにしたいです。再現性高く、どのようなソースコードや既存ドキュメントであっても、マークダウン形式にし、HTML 静的な HTML サーバーとして人間が見れるような、状況にしたいです。一旦はこんなところですかね。これから私と対話しながら、要件を整理していきたいですね。

## 2026-11-22 新しい設計書に何を書くか（選択式の質問への回答）

| 質問 | 回答 |
| --- | --- |
| 新しい設計書には、どの範囲の内容を書くか。（ISO/IEC/IEEE 29148 は要求仕様書の規格で、内部の作りの書き方は範囲外のため確認） | 要求仕様と内部設計の両方。「何をするか」は 29148 の構成で書き、「どう作られているか」は別の構成で書く。 |
| ソースコードと既存の設計書の内容が食い違ったとき、どう書くか。（例：設計書は30秒、コードは60秒） | コードの内容を書き、食い違いを一覧に記録して、人が後で確認できるようにする。 |
| 既存の設計書にしか書かれていない内容（コードからは読み取れないこと）を入れるか。 | 入れて、出どころを示す。「既存の設計書から取った内容で、コードでは確かめていない」と分かる印を付ける。 |

## 2026-11-22 品質と進め方（選択式の質問への回答）

| 質問 | 回答 |
| --- | --- |
| AI がソースコードを読んでも分からないことは、どう書くか。（例：3回までやり直す処理は読み取れるが、なぜ3回かはどこにも書かれていない） | 書かずに、不明点として記録する。設計書には読み取れた事実だけを書き、分からないことは不明点の一覧に残して、人が後で補えるようにする。 |
