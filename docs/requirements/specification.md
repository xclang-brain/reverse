# 要件と受入条件

[要求一覧](requirements.md) の要求（R-01 〜 R-16）を、実装とテストに使える要件に具体化したもの。

- 「元の要求」は、要求一覧の ID である。
- 「確かめ方」の A 〜 D は、5章のテストの種類である。
- 実現の方法は [プラグインの設計](../design.md) に書く。
- バージョンと変更履歴は Git で管理する。

## 1. 用語

| 用語 | 意味 |
| --- | --- |
| プラグイン | このリポジトリで作るエージェントプラグイン。名前は `reverse`。 |
| スキル | プラグインの入口。`/reverse:make-design-docs` で呼ぶ。 |
| 統括 | スキルの手順を進める、メインのエージェント。 |
| 担当エージェント | 統括が呼ぶサブエージェント。解析、変換、照合、執筆、検証の5つがある。 |
| スクリプト | スキルが実行する Python のプログラム（`revdoc.py`）。サブコマンドは `init`、`next`、`check`、`serve`、`stop`。 |
| 仕事 | スクリプトが担当エージェント1体に渡す作業の1件。 |
| 指示のファイル | 仕事ごとにスクリプトが書くファイル。担当エージェントは、これを読んで仕事をする。 |
| 出力先 | 新しい設計書と静的サイトを置くフォルダ。 |
| 作業フォルダ | 出力先の `.work/`。状態、指示のファイル、途中の記録を置く。 |
| 対象のソースファイル | ソースコードのフォルダのテキストファイルから、次を除いたもの：バージョン管理のフォルダ、出力先、シンボリックリンク、バイナリー、UTF-16 のファイル、空のファイル、2MB を超えるファイル、1行が 100KB を超えるファイル、文書、データ、ビルドの出力の拡張子（md、txt、html、csv など）のファイル。 |
| ユニット | ソースコードを解析する単位。同じフォルダのファイルを、上限までまとめたもの。 |
| モジュール | 内部設計書を書く単位。ソースファイルを直接含むフォルダ1つ。 |
| 既存の設計書 | 利用者が渡す PDF。Markdown に変換したものは `docs/legacy/` に置く。 |
| 新しい設計書 | 要求仕様書（`docs/requirements/`）と内部設計書（`docs/design/`）。 |
| 本文の行 | 段落の行、箇条書きの項目、表の行（見出しの行と区切りの行を除く）。コードブロックは、Mermaid を含めて、1つで1行と数える。 |
| 解析メモ | 解析担当が、ユニットごとに書く記録。 |
| 照合の記録 | 照合担当が、既存の設計書の行をソースコードと照らして分類した記録。 |
| 判定の記録 | 検証担当が、新しい設計書の本文の行ごとに書く判定。 |
| 印 | 本文に付ける決まった文字列。`【既存設計書のみ】` と `【判読できない】` の2つ。 |
| 材料 | 評価に使う、公開されている OSS のソースコードと仕様書の PDF。 |

## 2. 全体の流れ

1. 利用者が、スキルを呼び、ソースコードと PDF の場所を指示する。
2. スクリプトが、ソースコードをユニットとモジュールに分け、仕事の計画を作る。
3. 解析担当が、ユニットごとに解析メモを書く。変換担当が、PDF を1ページずつ Markdown に書く。
4. スクリプトが、変換した Markdown を組み立てる。照合担当が、その全部の行をソースコードと照らして分類する。
5. 執筆担当が、モジュールごとに内部設計書と機能の要求を書く。検証担当が、その全部の行をソースコードと照らして判定し、スクリプトが判定のとおりに直す。
6. 執筆担当が、全体の内部設計書と、要求仕様書の残りの章を書く。検証担当とスクリプトが、同じ方法で確かめて直す。
7. スクリプトが、食い違いの一覧、不明点の一覧、入口のページを作る。
8. スクリプトが、静的サイトを作り、その PC で表示する。統括が、結果を利用者に伝える。

ソースコードだけのときは、3 の変換と 4 を行わない。PDF だけのときは、3 の変換、4 の組み立て、7、8 だけを行う。

## 5. 受入条件

### 5.1 テストの種類

| --- | --- | --- |
| A | スクリプトの自動テスト（pytest）。モデルを使わない。 | 5.2 のテストがすべて通る。 |
| B | 読み込みのテスト。`claude` と `copilot` がある Linux の開発の環境で動かす。 | 5.3 をすべて満たす。 |
| C | 実際に動かす評価。材料を使い、Claude Code でスキルを最後まで動かす。 | 5.4 をすべて満たす。 |

### 5.2 A の主なテスト

入力は、テストの中で作る（合成のソースツリー、埋め込みテキストつきの PDF、画像だけの PDF）。合成のソースツリーは、C と C++（`.cpp`、`.hpp`。クラスと名前空間）のファイルを含む。

### 5.4 C の合格の条件

評価の進め方は、次のとおりとする。

### 5.7 開発者（AI）が決めた値と判断

- 5.4 の件数としきい値（30 件、10 件と8件、5件と4件、5 か所、9割、8割、2割、5%、5割、4割、3回）と、3章の行数、回数、割合（SR-80 の 2,000 ページを含む）は、開発者（AI）が決めた値である（H6）。変えるときは、SR とテストを直してから C をやり直し（6章）、前後の値と理由を評価の報告に載せる。
- 評価に使うモデルは、統括と担当エージェントが `claude-sonnet-5-5`、独立したエージェントが `claude-opus-5-5` である。独立したエージェントには、評価される側より性能の高いモデルを使う。
- 材料のコピーに 10 か所の変更を入れることは、「公開されている OSS を使う」（H4）の範囲に入ると判断した。変えるのは約 10 行で、ほかは OSS のままである。この変更に頼る条件（C-3、C-5）の結果は、ほかの条件と分けて記録する。
- A のテストは、テストの中で作る入力（合成のソースツリーと PDF）を使う。H4 では「AI が作る小さなサンプル」は選ばれなかった。上限ちょうどの行数、Shift_JIS のファイル、画像だけの PDF、100 万行のように、決まった形の入力が要るテストに限って使うと判断した。設計書の出来（C）と読み込み（B）は、材料だけで確かめる。
- C-14 のソースコードだけの場合に C++ の材料を使うことは、「C や C++ が中心」（H3）にもとづいて判断した。
- C-9 で `【判読できない】` の箇所を欠けに数えることは、「読み違いを直す」（H7）に最も近い解釈として判断した。
- SR-75 の許可を前もって与えることは、「最後まで自動で進める」（H4）に最も近い解釈として判断した。README に、通る範囲を書く。

## 6. AI の使い方

| 項目 | 内容 |
| --- | --- |
| 目的 | ソースコードと PDF の内容を読み取り、設計書の文章と図を書く。書いた内容を、ソースコードと照らして確かめる。 |
| 入力 | ソースコード、PDF のページの画像と埋め込みテキスト、ほかの担当エージェントが書いたファイル。どれも、指示のファイルで渡す。 |
| 出力 | 解析メモ、ページごとの Markdown、照合の記録、新しい設計書、判定の記録。どれも、決まった形式のファイルに書く。 |
| AI に任せないこと | 分け方、順番、形式の検査、設計書の書き換え、一覧の作成は、スクリプトが行う。 |
| 人の関わり | 利用者は、最初に場所を指示し、完成した設計書、食い違いの一覧、不明点の一覧を確認する。 |
| 分からないときの振る舞い | 推測を書かずに、不明点として記録する（SR-55、SR-60）。読めない文字には印を書く（SR-29）。確かめきれない既存の設計書の内容は、「既存設計書のみ」にする（SR-42）。読み取れる内容がない節には、決まった1文を残す（SR-50）。 |
| 誤りへの備え | 書く担当と確かめる担当を分ける。執筆担当が書いた全部の行を、ソースコードと照らす（SR-59 〜 SR-64）。根拠の場所と名前を、スクリプトが検査する（SR-23、SR-45、SR-61、SR-65）。 |
| 失敗したときの振る舞い | 不合格の出力は、理由を付けて渡し直す。3回目も不合格なら、失敗として不明点の一覧に載せ、先へ進む（SR-10、SR-11）。担当エージェントが出力を書けない環境では、止まって利用者に伝える（SR-12）。 |
| 評価 | 独立したエージェントとスクリプトが、5.4 の条件で確かめる。誤りは、種類ごと（記述、食い違い、既存の設計書にしかない内容、不明点、変換）に数える。 |
| 再評価の条件 | スキル、担当エージェントの定義、指示のひな形、スクリプトのどれかを変えたときは、C をやり直す。Claude Code、Copilot CLI、使うモデルのバージョンが変わったときは、B と C をやり直す。 |
